# 检索机理与未实现功能

本文回答两个问题：

1. 程序怎样从知识资产、标准目录和设备规则中找到相关内容或具体设备型式；
2. 当前版本哪些能力已经完成，哪些只是算法初筛，哪些尚未实现或必须换到生产环境验证。

内置公式本身的输入、知识出处、代码版本和双哈希追溯另见
[内置公式可追溯性](FORMULA_TRACEABILITY.md)。

## 1. 三类“查找”不能混用

系统实际存在三类查找动作：

| 类型 | 要解决的问题 | 输入 | 输出 | 是否能直接改变设备结果 |
| --- | --- | --- | --- | --- |
| 字段目录检索 | 某设备需要哪些参数、字段属于哪一层 | 设备族、字段主题 | 规范字段 ID、中文名、单位、别名、证据边界、查询模板 | 否，只帮助组织输入 |
| 知识资产检索 | 哪个资料片段可能解释公式、标准、部件或限制 | 自然语言查询、知识包范围、数量上限 | 来源、页码/行号、记录 ID、摘要、相关性、哈希和复用边界 | 否，只提供上下文 |
| 设备型式检索 | 当前工况应推荐哪种具体设备或系统型式 | 已规范化参数、确定性计算结果、选择特征向量 | 登记型式、候选、硬约束结果、调整方案和证据门 | 可以生成初步推荐，但不能自动升级为厂家最终型号 |

LLM 不负责上述任何一类检索的权威判定。它可以把程序返回的命中和候选组织成人类可读答案，但不能创造新的字段 ID、设备名称、候选 ID 或证据状态。

## 2. 字段目录检索

`app/app_core.py` 的 `knowledge_catalog()` 从设备目录和参数定义中建立查询目录：

1. 按 `family_id` 分成泵、换热器、塔、容器、压缩机、管线等设备族；
2. 按主题分成基础工况、计算输入、候选闭合、高级设计和正式证据；
3. 每个字段记录稳定的 `canonical_id`、中文标签、单位、人工输入角色和别名；
4. 为每个字段生成“设备族 + 中文字段名 + canonical_id”的查询模板；
5. 标记该字段是确定性/用户输入，还是正式发布前必须补充的同设备证据。

这个目录的作用是帮助 GUI 展开字段、帮助 Agent 提问和帮助知识检索形成查询，不负责生成字段值。

## 3. 知识包选择

知识检索只允许访问登记的本地包：

| `package_id` | 默认状态 | 内容 | 固定限制 |
| --- | --- | --- | --- |
| `equipment_core` | 默认选择 | 17 类设备参数、公式、证据边界和设计路由 | 提供方法与规则，不自动提供项目值或厂家最终型号 |
| `equipment_model_authority` | 默认选择 | 设备族、标准系列、型号状态机和厂家证据门 | 旧项目型号和跨位号数值不得迁移 |
| `design_standards` | 需显式选择 | 标准原文切片、页表、公式和适用范围 | 标准命名/方法不能替代同设备软件或厂家性能证据 |

选择策略如下：

- 只接受登记的 `package_id`；
- 最多同时选择 3 个知识包；
- 未打入当前运行包的知识包会直接报“不可用”，不会悄悄改查别处；
- 标准子图谱虽然物理上位于核心知识目录内，逻辑上仍是独立、显式选择的包；
- 相同物理根目录只扫描一次，避免重复结果；
- 检索上下文永远不能覆盖确定性状态或提升证据等级。

## 4. 查询规范化

`knowledge_search` 对请求执行以下前置处理：

1. 去除首尾空白，最长保留 500 个字符；
2. 空查询返回 `EMPTY_QUERY`；
3. `limit` 被限制在 1～20；
4. 中文逗号和英文逗号统一为空格；
5. 标准 SQLite 路由从查询中抽取英文标识、数字/版本号和长度至少两个字符的中文词，去重后最多保留 12 个词；
6. 显式选择的知识包必须是非空字符串数组，并经过存在性与可用性检查。

当前没有在这里自动使用 LLM 改写查询，也没有让模型补充同义词，避免未经审计的查询扩展改变检索范围。

## 5. 检索路由

程序按下面顺序运行，前一路由没有可用结果时才进入后续路由。

### 5.1 源码工作区向量索引

只有在源码工作区、没有运行冻结 EXE，并且存在 `query_workspace_vectors.py` 时才启用：

1. 用独立子进程执行查询，最长等待 30 秒；
2. 固定先取最多 20 个索引结果；
3. 根据 `source_path` 重新判断它属于哪个已选择知识包；
4. 不属于已选择包的命中被删除；
5. 截取用户请求的 1～20 项；
6. 成功状态为 `PASS_VECTOR_INDEX`，同时保留来源路径、标题、原始索引字段和名次。

这个路由服务于开发工作区。当前冻结程序不依赖它，所以不能把“源码环境有向量索引”写成“所有发布程序都有语义检索”。

### 5.2 标准 SQLite 只读检索

选择 `design_standards` 后，程序以 SQLite URI `mode=ro` 打开
`standards_knowledge.sqlite`，不会修改数据库。打开前先经
`data/database_authority_registry.json` 解析活动库，并核对文件大小、
SHA-256、`quick_check`、业务表、必需列和精确记录数；未登记、被替换或非活动库不会进入检索链。检索四种记录：

| 范围 | 查询内容 | 定位信息 |
| --- | --- | --- |
| `chunk` | 标准文本切片 | 文档、切片 ID、起始页和位置状态 |
| `table` | 表题和单元格文本 | 表 ID、页码、CSV 逻辑路径和表格定位状态 |
| `figure` | 图题 | 图 ID、页码和图像逻辑路径 |
| `formula` | 公式标签、题注和原始文字 | 公式 ID、页码和图像逻辑路径 |

数据库载荷包含 FTS5/trigram 索引表，但当前应用路由尚未消费这些索引，仍使用参数化 `LIKE`，不是 BM25。每个查询词出现在记录文本中记 2 分；按总分降序、记录路径升序排序。每种范围最多预取 `limit × 3` 条，再与其他路由结果合并。

检索响应同时返回 `standards_database_authority`。正常时给出数据库 ID、相对路径、SHA-256 和范围状态；注册表、载荷或路径验证失败时明确返回 `BLOCKED_DATABASE_AUTHORITY`，即使本地 Markdown/JSON/CSV 保底检索仍有结果，也不会把它伪装成 SQLite 权威命中。

每个标准命中还带有：

- `doc_id`、标准文件相对路径和原 PDF SHA-256；
- `source_kind`、默认证据等级、知识包状态和位置状态；
- 原始页码、逻辑资产路径和打包资产路径；
- 以查询词附近为中心、最长约 360 字符的摘要；
- `reuse_boundary`，明确是“只可路由”“需要复核”“只可借用方法”还是“仍需条款/表格适用性确认”。

紧凑运行包不复制所有图片和公式裁图，所以 `figure`、`formula` 命中通常只提供路由元数据，不能声称已经看过对应图像内容。

### 5.3 本地图谱文本检索

如果没有工作区向量命中，程序对已选择知识包中的 `.md`、`.json`、`.csv` 执行逐行扫描：

1. 忽略其他扩展名、缓存、Git 目录和脚本目录；
2. `equipment_core` 明确排除其内部的 `standards_graph`，避免绕过标准包显式选择；
3. 每个查询词出现在行文本中记 2 分，仅出现在文件名中记 1 分；
4. 命中记录保存知识包、相对路径、行号和最多 360 字符文本；
5. 按分数降序、路径和行号升序排序；
6. 与标准 SQLite 命中合并后截取 1～20 项。

返回状态为 `PASS_BUNDLED_GRAPH` 或 `NO_MATCH`，并明确当前模式是
`deterministic_standards_sqlite_and_local_search` 还是
`deterministic_local_search`。

## 6. 检索结果怎样进入 Agent

检索结果返回以下关键字段：

```text
status
mode
selected_packages
query_terms
result_count
hits[]
  ├─ rank / score
  ├─ package_id / source / scope
  ├─ path / line / page_1based / record_id
  ├─ document_path / source_pdf_sha256
  ├─ text
  ├─ package_status / location_status
  └─ reuse_boundary
limitations[]
```

Agent 可以：

- 引用命中的路径、页码、字段和限制；
- 把多个命中整理成公式解释、检查清单或待补证据；
- 根据字段目录生成更具体的后续查询；
- 向用户说明为什么某个结论只能作为方法或路由。

Agent 不可以：

- 把相关性分数解释成工程适用性或可信度；
- 用检索到的旧项目数值覆盖当前 Aspen/用户输入；
- 用标准中的设备名称直接替换程序候选；
- 把知识命中提升为厂家性能证据、正式机械计算或审批；
- 修改程序已经计算的数值、单位、阻断状态和哈希。

## 7. 设备型式检索机理

设备型式检索由 `scripts/equipment_design_match.py` 等确定性代码完成，不是普通全文检索。

### 7.1 建立统一输入

- 统一字段别名、单位、压力基准、相态和枚举；
- 拒绝含单位但无法识别、表压缺当地大气压、两相误走单相公式等输入；
- 区分 Aspen 直接值、用户值、确定性推导值、登记保底值和模型估算值；
- 计算输入包和来源谱系哈希。

### 7.2 先计算再找型式

程序执行登记公式，生成设备特征，例如：

- 泵：流量、总扬程、水力/轴功率、NPSH 差值、介质相态；
- 换热器：热负荷、LMTD、传热系数来源、初算面积和管数；
- 塔器：控制负荷、初算直径、级数/填料路线、塔高和有效面积；
- 管线：理论内径、标准 DN/外径、壁厚、实际流速、设计温压；
- 压缩机：绝压压比、入口体积流量、初算轴功率和喘振证据状态。

关键公式输入缺失时，程序保留已经完成的计算，并把设备置于“等待参数”或“等待专用路线”，而不是补一个看似合理的型号。

### 7.3 生成选择特征向量

选择向量只包含程序允许用于匹配的字段，并绑定：

- 设备族和终端型式候选范围；
- 当前工况与相态；
- 关键计算结果；
- 材料、结构、连接偏好；
- 特殊工况标志；
- 参数包、计算链和选择上下文 SHA-256。

自由文本型号不会直接进入特征向量。

### 7.4 候选过滤与终端规则

程序依次执行：

1. 设备族和应用类型过滤；
2. 相态、流量、扬程、压力、温度、尺寸等适用区间；
3. NPSH、喘振、相容性、计算完整性等硬约束；
4. 登记规则 ID 和条件 ID；
5. 标准目录点或登记工程规格候选；
6. 唯一终端型式检查。

只有具体登记型式可以成为 `recommended_type`。以下文字不得冒充终选：

- “非标准型设备”；
- “其他设备”；
- “待定型”；
- 仅有“泵”“换热器”“塔”这种设备族名称；
- LLM 自由生成、规则登记表中不存在的型号。

### 7.5 排序与状态

候选排序只在通过硬约束的登记候选之间进行。最终状态至少区分：

- 已形成具体工程型式；
- 计算完成但等待候选闭合；
- 候选存在但等待同设备正式证据；
- 工况超出单机/标准范围，需要系统调整；
- 关键计算被阻断。

候选排名不等于采购定型。泵厂家型号需要同介质/流量/转速性能曲线和 NPSHr；压缩机需要性能图和喘振裕量；换热器需要 EDR 或同等热工水力设计；塔器需要内件水力学。

### 7.6 超界时怎样检索修改方案

无法安全匹配单台标准设备时，程序不返回虚构的“非标准型”，而是在登记的系统方案中计算：

- 并联台数、串联级数、运行/备用数量；
- 每台目标流量、扬程、热负荷或面积；
- 分段、分壳程、分塔或改变工况的路线；
- 仍需厂家曲线、专项软件和专业审查的动作；
- 固定的 `J / provisional / TYPE_SCREENING` 警告。

这一步仍是规则检索和确定性计算，不是 Agent 自由提出方案。

## 8. 连接部件检索

设备型式完成后，`scripts/connection_component_selection.py` 使用以下条件查找登记的管件、法兰、垫片和密封路线：

- 介质和规范化相态；
- 组分、腐蚀性、毒性、可燃性、含固体等已验证物性事实；
- 设计压力、温度和压力基准；
- 材料、DN、连接方式和端部条件；
- 知识资产记录及其 SHA-256。

只有唯一登记终端记录才可返回。物性事实必须与当前流股、设备和连接 ID 绑定；仅有一个“看起来合理”的字段名不能成为证据。条件不足时保留缺口，不由 Agent 编造法兰等级或垫片材料。

## 9. 完整性与防篡改

在冻结程序中，检索前后还有以下保护：

- 运行时知识包清单检查文件数量、大小和 SHA-256；
- 数据库权威注册表固定活动/隔离/候选状态、消费者、表合同和允许范围；
- SQLite 执行完整性检查、表/列/记录数检查和构建清单检查，查询连接使用只读模式并显式关闭；
- 源码清单证明计算和检索运行的是哪组核心代码；
- 查询只允许进入登记根目录，并拒绝越出知识包根的路径；
- 全量知识资产装载有字符预算、扫描预算、截断标记和覆盖状态；
- 部分读取的文件不会伪装成“完整源文件哈希”；
- 设备候选、连接选择、客户投影和 Agent 控制记录分别计算哈希。

## 10. 当前检索尚未实现的能力

| 功能 | 当前状态 | 尚缺内容 |
| --- | --- | --- |
| 冻结 EXE 内完整语义/向量检索 | 未实现 | 工作区向量脚本只在源码环境可用；冻结程序主要使用 SQLite `LIKE` 和本地确定性文本评分。 |
| BM25/FTS 与向量混合排序 | 未实现 | 标准 SQLite 已携带 FTS5/trigram 索引表，但应用检索尚未调用，也没有把词法分数与向量分数校准合并。 |
| 中文分词、同义词和单位感知查询扩展 | 部分实现 | 已提取中英文词和数字，但没有完整化工词典、缩写展开、同义词图或单位维度查询器。 |
| 图片、流程图和公式视觉检索 | 未实现 | 紧凑包对图和公式主要保存题录、页码及逻辑路径，没有在运行时进行视觉嵌入/OCR 二次理解。 |
| 条款自动适用性判定 | 未实现 | 检索能定位条款或表格，不能自动证明项目版本、范围、材料、温压和例外条款均适用。 |
| 厂家在线目录/性能曲线检索 | 未实现 | 当前不联网抓取厂家数据，也没有厂家授权 API、曲线数字化和版本签名。 |
| 检索结果人工反馈学习 | 未实现 | 尚无多用户点击/采纳反馈、离线评测集和自动重排训练闭环。 |
| 跨项目知识库和权限检索 | 未实现 | 当前是本地允许列表知识包，没有组织级权限、租户隔离和项目保密检索。 |

### 11.1 2026-08-20 Agent 与设备链增量验收

本轮把“能连通模型”和“模型建议能够安全进入设备链”分开验收：

- 当前源码全量回归为 499 项通过、1 项按环境条件跳过；

### 11.2 v2.4.3：Aspen registry-driven 提取

本节实现已经进入 v2.4.3。它解决的是“提取到了什么、为什么这样解释、哪些地方没有覆盖”的可审计性；发布和本地测试通过不代表已经完成所有生产 Aspen 版本的兼容验收。

| 项目 | v2.4.3 实现 | 失败或兼容边界 |
| --- | --- | --- |
| 字段注册与模块识别 | 流股和已登记 block 类型按 registry 请求字段，不再只依赖一组硬编码通用字段；每个字段观察记录 `path`、`unit`、`status`、`provenance` | 未知模块保持 unknown/unmapped，不套用笼统设备角色或虚构 `process_function`，也不以未知对象“完整度 100%”冒充已覆盖设备 |
| 未映射发现 | 未映射节点只保留 `value_type`、`value_size`、`value_sha256` 等元数据，用于定位新增注册需求 | 默认不保存 raw value；敏感或超长值不会因为 discovery 进入旁车 |
| 覆盖报告 | 独立 `aspen_extraction_coverage.json` 汇总 requested/found/missing/error/unsupported、注册字段命中率、未映射节点和逐字段证据 | 主案例与 worker 输出记录旁车路径及 SHA-256；旁车不是设备计算输入，也不能把缺失字段提升为已找到 |
| v1 兼容 | 主 `aspen-equipment-export-v1` 严格维持原有顶层、`equipment_map` 和四字段 composition 形状 | 新追溯字段只进入覆盖旁车，避免旧 v1 消费者因额外字段或 unknown 的空工艺功能失效 |
| 失败门 | Streams/Blocks 根节点访问、枚举、缺失或截断异常会阻断 COM 提取；没有物料流不再空集 PASS | 根提取失败优先形成 `BLOCKED_COM_EXTRACTION`，不能被后续 transport 状态掩盖 |
| 组分与预算 | 非法组分、不闭合、枚举异常不能标成完整向量，也不会把部分向量写入主 bundle；全案例节点数和元数据字节设有预算 | 预算耗尽、发现错误或截断会阻断完整度或转为不可评分，不允许静默给出完整覆盖结论 |

当前本地证据是 Aspen importer 定向测试 52/52，以及 Aspen 相关联动测试 137 项通过、1 项按环境条件跳过；这不是统一全量回归统计。真实生产机仍需验证不同 Aspen 版本的 HAP/COM 节点与单位行为、集合索引和异常语义、用户自定义或厂家模型、真实多相组分树，以及大案例遍历性能和预算阈值。完成这些验证前，只能称为本地实现和严格 fake-tree 合同通过，不能称为生产通用兼容。

## 14. 怎样判断某项功能以后真正完成

不能只看界面有没有按钮。每项能力应同时满足：

1. 有明确输入合同、单位和失败状态；
2. 有确定性实现或受控外部工具接口；
3. 有真实项目/生产环境样例；
4. 有正常、缺项、越界、篡改和回归测试；
5. 输出带来源、版本、哈希和证据边界；
6. GUI、CLI、报告和客户一览表显示一致；
7. 用户能修改、重算、恢复默认并看到影响范围；
8. 不成功时明确阻断或警告，不能降级成含糊“非标准型”。

因此，本项目把“代码存在”“测试通过”“生产环境验证”“正式工程可采用”作为四个独立状态管理。
